# At-rest protection with a passphrase

The laptop encrypts its root filesystem with LUKS and unlocks it at boot by typing a passphrase. The tower does not — it is a desk-bound machine that does not travel, so the adversary this defends against (powered-off possession) does not apply, and the cost of typing a passphrase at every boot is paid for nothing. The boundary is the machine's portability, not a policy difference between hosts.

The adversary is a thief who holds the disk and the machine together, powered off. The design is the smallest thing that covers that adversary: a passphrase at boot, a plaintext ESP, and no hardware secrets. The swapfile at `/swapfile` sits on the root filesystem, so it rides along inside the LUKS container for free — no separate configuration.

The passphrase is typed at every boot. `console.keyMap = "de"` propagates into the systemd initrd automatically (NixOS 26.05 makes systemd initrd the default), so `systemd-vconsole-setup.service` applies the German layout before `systemd-ask-password` reads a single keystroke. No `boot.initrd.*` keymap option is needed.

A recovery key in a second keyslot covers the forgotten-passphrase case. It is generated by `systemd-cryptenroll --recovery-key` and stored in the Bitwarden vault — reachable from the tower, the phone, or any device, and unreachable from a stolen, powered-off laptop, because the vault lives *on* the encrypted disk. The circularity is broken by the vault being sync'd to other machines.

## Considered Options

**Rejected: TPM2 auto-unlock.** A TPM-only keyslot hands the disk to whoever holds the machine: the attacker presses power and the TPM unseals the key. That is worse than plaintext, because it preserves the ritual of unlocking while guarding nothing.

**Rejected: TPM2 + PIN.** A PIN unsealed from the TPM is a secret the thief lacks, so it does defend. But it is the passphrase with extra steps and a shorter, weaker secret, and it needs `systemd-cryptenroll` configuration that NixOS does not generate — additional hand-written config for no gain over typing a passphrase.

**Rejected: a FIDO2 security key.** A second keyslot on a hardware token survives a forgotten passphrase. It also costs hardware to buy, a thing to carry, and a failure mode — the token dies and the machine is a paperweight until the recovery key is found. The recovery key already covers the forgotten-passphrase case with nothing to carry.

**Rejected: the fingerprint sensor at the decryption gate.** A fingerprint match is a boolean from the sensor, not key material; there is nothing to enroll into a LUKS keyslot. And even if the sensor could export bytes, fingerprints are not secrets — the thief has the machine, and the machine has your prints on it. The sensor stays where it belongs, on the authentication side of the line ADR-0008 draws: the lock screen, *after* the disk is open.

**Rejected: encrypted `/boot` plus Secure Boot.** UEFI firmware needs a FAT ESP to load `BOOTX64.EFI`, and Limine has no LUKS decryption capability — the nixpkgs Limine module actively rejects an encrypted `/boot`. So the ESP must stay plaintext regardless. Encrypting it would defend against evil-maid tampering, which is a hardware-forensics bar this project set out of scope. The ESP holds only kernels and initrds from the public Nix store; encrypting them defends against tampering, not reading, and that is a different threat model.

**Rejected: systemd-initrd just for this.** systemd initrd is now the nixos-unstable default (NixOS 26.05), so there is nothing to opt into — the system already uses it. Scripted initrd is deprecated and scheduled for removal in 26.11. The classic stage-1 handles LUKS passphrase unlock out of the box; so does systemd initrd, with no extra configuration.

**Rejected: extending to the tower.** The tower is a desk-bound machine; it does not travel, and the powered-off-possession adversary does not apply. Unlocking it at every boot is a convenience cost with no matching threat. If the tower ever moves, this decision is revisited.

## Consequences

**This removes the premise behind ADR-0006 and ADR-0008.** ADR-0006 argued the kernel was right to refuse hibernation because a hibernation image on an unencrypted root would be RAM in the clear. The root is now encrypted, so the swapfile holding that image is encrypted too; the exposure half of that argument dies. The kernel gate (`secretmem_active()`) does not ask whether the disk is encrypted, so no-hibernation stands — see the amendment note on ADR-0006. ADR-0008 justified the fingerprint's "convenience, not security" label with "the root filesystem is unencrypted, so anyone holding the machine reads it from a USB stick regardless". That sentence dies; the conclusion survives on a corrected premise — a fingerprint produces no key material and cannot unlock the decryption gate. See the amendment note on ADR-0008.

**The swapfile becomes encrypted for free.** The laptop's 20 GiB swapfile lives inside the root filesystem, so it sits inside the LUKS container. Paging no longer writes plaintext to disk. Nothing needed declaring for this; it is a consequence of where the swapfile already was.

**Migration is a wipe-and-reinstall.** There is no in-place conversion from plaintext ext4 to LUKS on this layout; the README's install procedure is the migration path. After reinstalling, `regen-hardware` rewrites `_hardware-generated.nix` with the `cryptroot` mapper as `/` and the `boot.initrd.luks.devices."cryptroot"` entry. The `luksExpected` flag in `hardware.nix` is flipped to `true` as the last step, and from then on `nix flake check` fails if the root stops being a LUKS mapper device.

**The ESP stays plaintext and that is by design, not by oversight.** Limine cannot decrypt, and UEFI firmware cannot load from an encrypted volume. The ESP holds only the bootloader, kernels, and initrds — all public Nix store artifacts. Encrypting them would defend against tampering, which is out of scope.

**The recovery key lives in Bitwarden, not on the machine.** The vault is cloud-synced and lives on other devices too, so the key is reachable from the tower, the phone, or any device — and unreachable from a stolen, powered-off laptop, because the vault is *on* the encrypted disk. See the intro for the full argument.
